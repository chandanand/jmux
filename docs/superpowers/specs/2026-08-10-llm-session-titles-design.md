# LLM-generated session titles

Date: 2026-08-10

## Problem

A session's row 1 shows its tmux session name, and that name is a slug. On the
issue flow it is `tra-123` — `sessionNameTemplate` defaulting to `{identifier}`,
or the tracker's own `branchName` when it has one. On the hand-made flow it is
whatever the human typed at `Ctrl-a n`. Neither says what the session is *for*.

The identifier is not useless — it is the one string that ties the row to a
ticket, an MR and a worktree — but it answers "which record is this" rather than
"what is happening here". A sidebar of eight rows reading `tra-118` through
`tra-131` requires the human to hold the mapping themselves, which is precisely
the work an always-visible surface should be doing for them.

The information to answer the second question is already on hand at the moment a
session is created: the issue's title and description, or the first thing the
human asked the agent to do. Nothing reads it.

## Approach

A **title** — a short human phrase, generated by a model — layered over the
session name, which does not change.

The one-name rule stays intact. `resolveIssueSessionName` still produces the
session name, and that name is still the branch and still the worktree
directory; Linear's `branchName` still links back to the ticket it came from;
`pinnedSessions` and every other config key still key on it. The title is a
second string that renders in front of it, and the whole off-state is
`title ?? name`.

That fallback is doing more work than it looks. No command configured, no title
generated yet, a call that failed, a call that returned nothing usable — all
four render exactly what ships today. There is no degraded rendering mode to
keep working, and no second layout to maintain.

## Storage

`@jmux-session-title`, a session-scoped tmux option.

Same reasoning as the agent-state options and `@jmux-browser`: **the option is
the protocol**. `ctl` has no IPC to the running TUI, so anything both halves
need to see has to live where tmux can hold it. It survives a jmux restart, it
survives the TUI being killed and reattached, and `ctl session list` returns it
without jmux having to arrange anything.

Session-scoped rather than pane-scoped, unlike `@jmux-agent-state`. That option
is pane-scoped because a session can host several agents in splits and a
session-scoped write would let the last one clobber its siblings. A title has
the opposite shape: one session, one row, one name. There is nothing to roll up.

Beside it, `@jmux-title-signature` holds the signature of the input the current
title came from — or the literal `manual` when the human named the session
themselves. It is what makes the cache and the rename rule outlive a restart;
see "Triggers" and "Decisions taken without being asked" below.

## Generation

### Transport

One global config block. The command is a property of the user's machine and
their model access, not of a repo, so it sits beside `agentScreenDetection`
rather than in `repoDefaults`:

```jsonc
"sessionTitle": {
  "command": ["claude", "-p", "--model", "haiku"],
  "timeoutMs": 60000,
  "maxChars": 32
}
```

**The command is the entire provider story.** jmux writes the prompt to stdin
and reads one line from stdout. `codex exec`, `llm -m gpt-4o-mini`,
`ollama run qwen2.5` and a shell script the user wrote all work with no jmux
code, and the model choice is a flag the user already controls. There is no
provider registry, no API key handling, and no second authentication story in a
tool that currently has none — the command reuses whatever the user has already
authenticated.

**argv rather than a shell string**, so there is no quoting question and no
parser. `shell-quote.ts` only *quotes* — it has nothing that parses a command
line — and `diffPanel.hunkCommand` is a bare binary name handed to `Bun.which`,
so there is no precedent to follow into writing one.

**`command` unset is off, and the value is the switch.** No separate boolean can
disagree with it — the same rule `showUnstartedInSidebar` follows, and for the
same reason.

### Three inputs

| Input | Source | Available when |
| --- | --- | --- |
| Issues | `orderedSessionIssues` — identifier, title, description | the session has linked issues |
| First prompt | `@jmux-prompt`, pane-scoped (see below) | an agent with hooks has been prompted |
| Git | repo name, branch, `git log` against the base branch | always, for a session in a worktree |

Resolved in that order, strongest first. An issue is the most specific statement
of intent available; the human's first prompt is the next; the git context is
the last resort and is frequently thin — a fresh worktree on a branch called
`t3code-550aceea` with no commits yet says almost nothing, and a title generated
from it will be correspondingly vague. That is acceptable as a floor, not as the
common case.

`@jmux-prompt` is pane-scoped, because the hook that writes it knows a pane and
not much else — the same reason `@jmux-agent-state` is. The generator asks for a
session, and takes the **first non-empty value across that session's panes**.
Deliberately not an `outranks()` rollup: that helper ranks by *urgency*, which a
prompt does not have, and the hook writes each pane's value exactly once, so
first-non-empty is already deterministic.

pi has no prompt event in its extension API — the same gap that already stops it
reporting `waiting` — so pi sessions with no issue land on the git tier. This is
why the git tier exists rather than being cut.

### Triggers, and the signature that gates them

A naming call fires when a session's **input signature** changes and jmux has
not already tried that signature.

For the issue tier the signature is `issueLinkSignature(ids)`, which already
exists and which `PollCoordinator` already re-resolves on. A session that grows
from one ticket to five gets re-titled from the wording of the first ticket to
something covering the feature — which is the behaviour the multi-issue link
was built for and the `+N` badge already promises. Re-ordering or re-spelling
the same set is not a change, because the signature sorts and normalises.

For the prompt and git tiers the signature is a hash of the input text.

**A failure caches under its signature too.** This is the rule the image store
already follows — never re-enter a fetch for a URL already seen, *including a
failed one* — and it exists here for the same reason: the poll runs
continuously, so a model that timed out once would otherwise be asked again on
every tick forever. A new signature is a new attempt; the same signature is not.

**The title never re-generates from the work itself.** No periodic re-naming
from pane output or the accumulating diff. A name that changes under the cursor
while the human is reading the sidebar is worse than a name that is slightly
stale, and "recently" has no honest definition here.

### Failure, and what it must never do

One call in flight per session. Global cap of two concurrent, so a first run
against twenty existing sessions drains rather than forking twenty subprocesses.
Bounded by `timeoutMs`.

A naming failure is **silent**. It does not raise the session's attention flag —
that flag means the human's work needs them, and a model that did not answer is
not the human's work. It does not block or fail provisioning: `issue-provision.ts`
creates the session first precisely so nothing has to wait, and a title is the
least urgent thing in that sequence.

### Output is validated, not trusted

First line only. Strip surrounding quotes, backticks and a trailing period. Cap
at `maxChars`.

**`maxChars` is one number doing two jobs**: the budget stated in the prompt and
the cap applied to the reply. This replaced a design where the prompt asked for
"at most eight words" while the cap counted characters — two limits in different
units, which is a drift waiting to happen, and eight words is anywhere from 30
to 70 columns.

The default is 32, set against the sidebar rather than against what a model can
write. The earlier reasoning here was that the palette and `ctl` have room for
more, so the cap should be generous and each surface should truncate to what it
has. That was wrong about which cost matters: a title cut off at the surface
you actually read it on says less than a shorter one that fits, and the wider
surfaces lose nothing by showing a short phrase. Asking for the budget also
means the model chooses what to drop, which it does better than `slice()`.

A budget is not a guarantee — a model that overshoots is still cut at the cap.

Anything empty after that is rejected and the session keeps its real name — the same fallback as never having called at all, which is what keeps
this to one code path.

## The hook change

`UserPromptSubmit` is already an installed event for Claude Code and Codex; it
writes `running`. It gains a second step that captures the prompt, and three
things about it are load-bearing.

**The state write goes first.** Reading the prompt means reading the hook's
stdin, and a `cat` with nothing on the other end blocks until the hook's 5s
timeout. Ordering the capture after the state write means the worst case is a
missing title, not a RUNNING indicator that appears five seconds late. This is
the one event where the "one tmux process per fire" property in `commands.ts` is
deliberately relaxed: `UserPromptSubmit` fires once per human prompt, which is
rare, unlike `PreToolUse`.

**The capture is guarded twice, with the idiom already in the file.**
`writeRunningIdempotent` reads `show-option -p -qv` — which, unlike a format
expansion, does not inherit from the session — and skips its write when the
value is already what it would set. The capture uses the same read for both of
its guards:

- Skip if `@jmux-prompt` is already set on this pane. That makes the stored
  value the *first* prompt rather than the latest, so a title is stable for the
  life of the session, and it means the capture runs once instead of on every
  prompt.
- Skip unless `@jmux-title-capture` is set. jmux writes that server option at
  startup from `sessionTitle.command`, so **a user who has not configured
  titling never has their prompt stored at all**, and turning titling off stops
  the capture without reinstalling hooks. Hooks are installed once and cannot
  read jmux's config; a server option is how they ask.

**The hook stores the raw stdin JSON and jmux parses it.** Extracting a field
from JSON in a shell one-liner needs `jq`, which is not guaranteed to exist, and
a hand-rolled `sed` would be wrong on the first prompt containing a quote.
Parsing belongs where parsing is easy. Truncated with `head -c 4000` at the
write so a pasted stack trace does not become a tmux option value.

`detectInstalledKind` compares the whole hook entry including its command text,
so an existing install reads as `partial` and `--install-agent-hooks` rewrites
it. No migration is needed beyond that; a stale hook simply keeps reporting
state and stores no prompt.

## Rendering

### The session row

```
Fix stale cache headers on CDN            P
TRA-123 +4 · In Review        3m    !412  ●
45k                                 WAITING
```

**Row 1** is the title, or the real name when there is none, truncated with `…`.
The mode badge (`P` / `A` / the compaction marker) moves to the right edge,
which is the slot the issue badge vacates.

**Row 2 leads with the issue badge**, moved down from row 1 unchanged —
`formatIssueBadge` and the `orderedSessionIssues` construction behind it are not
touched, so the badge and the disclosure below it still cannot name different
issues. Then the stage word, the timer, the MR id and the pipeline glyph.

**Row 3 is untouched.** It still exists only for a session with a live agent
(`itemHeight`, `sidebar.ts:786`).

**The branch leaves the sidebar.** It was only ever visible *as* row 1's session
name, and row 1 is now the title; keeping it on row 2 at a 26-column default
would truncate it to nothing useful while displacing the timer, which is what
tells the human an agent has been stuck for forty minutes. On the wtm flow the
session name still *is* the branch, so row 1 shows it until a title supersedes
it, and the ghost preview's pre-flight still names the branch a not-yet-started
issue would get. Nothing renders a running session's branch anywhere else — the
info panel has no branch field.

**Row 2 drop order, right to left:** timer → stage word → stage glyph → drift
marker → MR id → and never the issue badge. The badge is now the row's identity;
a row that has dropped it says nothing about which work it is. This extends the
existing order rather than replacing it — the stage field's rule that it
outranks the branch is unchanged in substance, since the branch is gone.

Everything else on row 2 keeps working unchanged: `stageInHeader` suppression
under `group=stage`, the `→Done` drift form and its terse `!`, the disclosure
chevron and its click target, which move down with the badge onto a row already
mapped in `rowToSessionIndex`.

### Other surfaces

The command palette, the Command Center's pane labels (`buildPaneLabel` — not
`glass/tabs.ts`, which is the Diff/Overview strip and holds no session names)
and `ctl session list` lead with the title and keep the real name as secondary
text; `ctl` returns both as separate fields, because a machine consumer needs
the one that addresses a tmux session.

**Palette fuzzy match runs over title and name both**, so the slug never stops
being typeable. A human who has typed `tra-123` for two days should not have to
learn a new string to reach the same session.

`sortBy: "name"` sorts on what is displayed — `SessionSortInfo.name` is fed the
display name. Sorting a visible list by a hidden key is the kind of inertness
`sectionedViewNotice` exists to refuse.

## Modules

- **`src/session-title/prompt.ts`** — pure. `buildTitlePrompt(input)` over the
  three input shapes, and `parseTitle(raw)` for the validation above. No
  subprocess, no tmux, no clock.
- **`src/session-title/generator.ts`** — the queue. Signature cache holding
  successes *and* failures, single-flight per session, concurrency cap, timeout.
  Spawn is injected, so this tests against a fake that returns a canned line, a
  hang, and a non-zero exit.
- **`src/session-view.ts`** — `SessionView` gains `title`; `linearId` moves to
  row 2; `branch` drops.
- **`src/sidebar.ts`** — row 2's field set and drop order; row 1's badge slot.
- **`src/agent-hooks/commands.ts`** — the guarded capture on `UserPromptSubmit`.
- **`src/config.ts`** — the `sessionTitle` block.

## Testing

Unit tests at the level the suite already works at. `prompt.ts` is pure and
tests directly. `generator.ts` tests against an injected spawn: a title comes
back and is stored; a timeout leaves the name alone and is not retried under the
same signature; a changed signature *is* retried; two sessions do not exceed the
concurrency cap. The sidebar's existing render-plan tests cover the row-2 change
directly, at several widths so the drop order is exercised rather than asserted.
`commands.ts` has a test asserting the exact shell string, which is how the
existing hook commands are covered.

No integration test. Nothing here touches tmux protocol parsing, grid math or
asset resolution — the three places where the unit tests either side of the glue
have historically all passed while the feature was broken.

## Decisions taken without being asked

**No backfill sweep.** On first run against existing sessions, titles generate
as each signature is first seen. That is a burst, drained at two concurrent, and
a one-time cost. Naming lazily only when a session is looked at would be more
machinery for less.

**A hand-typed rename wins permanently.** Renaming a session unsets
`@jmux-session-title` and stamps `@jmux-title-signature` with the literal
`manual`, which the generator skips. The sentinel lives in a tmux option rather
than an in-memory set precisely so "permanently" survives a restart: an explicit
act beats a generated guess, and a title reappearing over a name the human had
just typed would be the worst behaviour in the feature.

That signature option earns its place twice. It is also the cache key that stops
a restart re-titling every session, which is what keeps the burst below a
one-time cost.

## Non-goals

- Titling that evolves with the work. Decided against above.
- A provider registry, model picker UI, or API key storage. The command string
  covers every provider the user has, and adding a second auth story to jmux
  would be a larger change than the feature.
- Changing the tmux session name, the branch or the worktree directory. The
  one-name rule is untouched.
